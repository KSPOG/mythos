# NPC Architects 0.2.8 — experimental source prototype
Forge 1.21.1-52.1.5 / Java 21. No custom client content. Vanilla connection not tested.

## Build
Install Java 21 and obtain the official Forge 1.21.1-52.1.5 MDK from https://files.minecraftforge.net/net/minecraftforge/forge/index_1.21.1.html . Extract its Gradle wrapper (`gradlew`, `gradlew.bat`, `gradle/wrapper/`) into this directory. Use the unmodified MDK wrapper. Run `gradlew.bat build` (Windows) or `./gradlew build` (Linux). Install the generated JAR from `build/libs` on a test Forge server only. The Forge 52 port requires a successful CI build and in-game testing.

## Test
Use an operator on a flat, empty test world. `/architect house 7 7` spawns one builder and creates a house three blocks southeast of your feet. `/architect status`, `/architect pause 1`, `/architect resume 1`, `/architect cancel 1`. Cancel does not undo blocks or despawn the worker. Jobs are saved in the world directory. Keep chunks loaded. A blocked job can be resumed after clearing obstructions or moving the worker. Missing workers do not respawn. Vanilla villager AI may compete with navigation; scaffolding is not implemented and high blocks may stall. No claim integration, line-of-sight enforcement, material consumption, schematic import or custom GUI. Use backups; do not deploy on a production world.

## Diagnostics
`/architect ping` is available to all players; construction and status remain operator level 2. The server log reports initialization, command registration and startup. `pack.mcmeta` covers Minecraft 1.21.1 data (48) and resource (34) pack formats.

## Construction selection
Stand at the first and opposite corner (inclusive) and run /architect pos1 and /architect pos2. Same Y uses height 5; otherwise the inclusive Y span is the height. Width/depth 5–15; height 4–12. /architect rotate 0|90|180|270 changes orientation; selection retains its physical footprint. /architect preview house emits a one-shot particle preview and counts blocked positions; /architect build house starts the job. Direct /architect house 7 7 5 uses a +3 X/Z origin and current rotation. /architect undo [id] pauses and removes only recorded placements still matching the expected block state; it does not restore pre-existing blocks, cannot distinguish identical player replacements, and older jobs lack undo history. Selections reset on restart/dimension change. Undo without an ID targets the latest job globally (operator-only). No scaffolding or claim integration; back up your test world.

## Automatic clearing
New jobs survey the entire rotated rectangular volume, then clear mismatched blocks top-down before building. Matching blueprint blocks remain. Block entities, liquids and unbreakable blocks are rejected; no drops are generated. Clearing uses NPC reach and navigation, no teleportation, no changes outside the footprint. Undo attempts to restore cleared block states if the cell is empty; numeric block-state IDs assume the same registry on restart. Back up the world: ordinary player-built blocks inside the selected volume can be removed; claim protection is not integrated. Existing jobs keep their old progress and do not automatically enter clearing. Preview counts clearing and protected positions.

## Builder protection and recovery
Architect workers are invulnerable and persistent; hostile targeting is canceled for tagged builders. Existing loaded job workers are protected on the next management tick. Confirmed worker death triggers replacement at a safe loaded position when a running job resumes. Missing workers may simply be unloaded, so they are not automatically replaced. For a worker known to be gone, stand near the site and use `/architect recover <id>` as an operator; it preserves clearing and building progress. If the old worker was merely unloaded, a manual replacement can leave an orphan villager. No normal villagers are modified. Protection does not protect nearby players or buildings, and administrative removal can still require recovery. Runtime behavior requires testing.

## Elevated construction controller
Builders no longer use ordinary villager wandering goals. During active clearing/building, controlled movement uses eye-height reach and collision-checked elevated work positions with temporary hovering. If a direct movement route is blocked, the controller may reposition the builder to a verified empty loaded stance near the current target. This is a creative-style fallback, not scaffolding or survival pathfinding. Gravity is restored when paused, blocked, cancelled or finished; builders remain stationary rather than wander. Existing jobs retain their blueprint cursor; use `/architect resume <id>` for blocked jobs. Layer completion and exact blocking reasons are logged. In-game movement still requires verification.

## Custom schematics (v0.2.8)
Place Sponge v2/v3 `.schem` files in `<world>/npcarchitects-schematics/` (created automatically). Use filename stems containing letters, numbers, underscores or hyphens. `/architect schematic list`, `/architect schematic info <name>`, `/architect pos1` to select the minimum corner, `/architect rotate 90`, `/architect schematic preview <name>`, `/architect schematic build <name>`. If pos1 is not selected, the origin is three blocks southeast of the player. Pos2 is not used. Imports normalize to the minimum corner and ignore the file offset, metadata and biome data. No fixed gameplay dimension or volume cap. Sponge unsigned-short dimensions, Java array indexing, world bounds and available heap still apply. NBT parsing budget defaults to one quarter of JVM max heap (minimum 16 MiB), configurable with -Dnpcarchitects.nbtBudgetBytes=<bytes>. Only vanilla block states supported; block entities, fluids and entities rejected. Legacy .schematic and .litematic not supported. No DataFixer migration; use compatible 1.21.1 blocks. Air is intentionally cleared across the whole volume; preview before building. Imported plan stored with the job so restarts and undo do not depend on source file. Neighbor updates, gravity and unsupported multipart blocks may affect final fidelity; in-game testing required. Existing house jobs unchanged.

### Map-scale jobs
Large imports save the immutable plan separately under `<world>/npcarchitects-plans/`; preserve this directory with world backups. Survey runs in bounded batches before any clearing, with expiring chunk tickets to load or generate the current work region and keep the builder active. Preview is sampled in currently loaded chunks, not a complete survey. Large jobs may safely reposition builders between distant working positions. Construction remains one block at a time; undo history and decoded plan still consume memory and job checkpoints grow with modifications. Undo requires affected chunks to be loaded; map-scale undo streaming, asynchronous import, and multi-worker throughput remain future work. No claim protection. Do not import untrusted files or run without backups.

### Autonomous chunk loading for all builders
Every running job (house or schematic) refreshes expiring region tickets around its worker and current work target, including after server startup. Tickets move with the worker, and crossing a chunk boundary checkpoints the saved worker position. Tickets are removed when paused, blocked, cancelled, completed, undone, storage fails or the server shuts down. Missing workers are not duplicated automatically merely because their chunk is loading; legacy jobs without worker coordinates reload the build origin and may require manual recovery. The server must remain running and ticking; this does not override host shutdown or server pause behavior. Initial house creation still requires a loaded site; subsequent work does not require a nearby player. Chunk generation and multiple concurrent jobs increase server load. Runtime verification with all players disconnected is required.

## Automatic builder cleanup
Completed, cancelled and undone jobs remove the associated villager by saved UUID without drops. Existing terminal jobs are cleaned on management ticks; unloaded builders are prevented from joining the world when their chunks load. Paused and blocked jobs retain their worker. Terminal job records and undo history remain, and cancellation/completion do not release the reserved site. No extra chunks are loaded solely for cleanup. Runtime verification required.

### Completion notifications
New jobs record the initiating player's UUID. When construction reaches DONE and its state is saved, the owner receives a green completion chat message containing the job ID, schematic name (or house), blueprint block count, dimension and origin coordinates. If the owner is offline, the persisted completion is delivered when they return; normal server ticks also retry pending notifications. Jobs created before v0.2.8 have no owner, so newly completed legacy jobs notify online operators instead (pending until one is online). Previously completed jobs are not retroactively announced. Delivery is best-effort; a crash or failed save immediately after sending may repeat a notice. Cancelled and undone jobs do not announce successful completion.

## Faster surveying (v0.2.8)
Read-only surveys run every server tick instead of every ten ticks. Default shared maximum 16,384 positions per tick, with a soft 4 ms processing budget checked every 32 positions; round-robin allocation across running surveys. Cross already-loaded chunk boundaries in one pass, refresh tickets only at transitions, stop on an unloaded chunk and retry. Empty positions bypass blueprint lookups. Survey-only checkpoints every 100 ticks (5 seconds at 20 TPS) and on completion, pause, shutdown or blocked state; other job saves may also persist progress. Crash may repeat read-only checks. JVM overrides: -Dnpcarchitects.surveyBatch=16384 -Dnpcarchitects.surveyBudgetMs=4 (1–20 ms). The first blueprint lookup cache initialization, chunk generation and synchronous save operations are not bounded by the soft budget. No change to block placing/clearing cadence or protection policy. Runtime benchmark required.

## Faster Architect travel (v0.2.8)
Movement runs every tick while approaching a pending construction or clearing target; placement and destruction retain their ten-tick cadence. Default movement step 0.65 blocks per tick (theoretical 13 blocks/sec at 20 TPS versus 1.3 previously). Configure `-Dnpcarchitects.moveSpeed=0.85` in user_jvm_args.txt; finite values clamped to 0.1–1.0. Movement still uses collision-aware entity motion, verified safe stance fallback, loaded swept chunks and world bounds; no movement while paused, terminal, surveying or storage failed. Existing safe repositioning remains available when direct travel is obstructed. Actual speed depends on collisions, server ticks and client interpolation. Runtime testing required.

## Construction teams (v0.2.8)
`/architect add <jobId> <count>` adds workers to an existing nonterminal project from safe positions near the operator in the job dimension. Default team cap 16 total, configurable via `-Dnpcarchitects.maxTeam=32` (1–64). Survey and terrain clearing remain coordinated by the original worker; additional workers join placement after clearing. Each receives a distinct block reservation within the current layer, with a shared layer barrier, persistent out-of-order completion and common undo history. Per-worker chunk tickets, death recovery and terminal cleanup. Missing unloaded workers are not duplicated; recover still targets the primary worker. Placement maximum remains two blocks per second per worker at 20 TPS. Existing jobs default to one worker. Team size and out-of-order progress shown in status. CI and actual multiplayer construction testing required; no measured scaling claim.

### Status visibility
`/architect status` hides CANCELLED and UNDONE jobs, including old saved records; DONE, RUNNING, PAUSED and BLOCKED jobs remain visible. `/architect status all` includes the full history. Terminal jobs display zero assigned active Architects (unloaded NPC cleanup may still be pending). Filtering does not delete job records, release reserved sites, change IDs, or remove undo history.

## Parallel clearing (v0.2.8)
All team members participate in clearing after the shared survey. The coordinator preserves the existing top-down order within each clearing slice; distinct reservations and durable out-of-order clearing indices prevent duplicate work. A bounded scan skips air and already-matching blocks, while each worker can remove up to one obstruction per ten ticks. Protected blocks, liquids, block entities and world boundaries remain checked. Entire clearing phase must finish before placement. Existing in-progress jobs retain their cursor; no reset required. Shared undo history retains actual removed blocks. Runtime throughput and chunk loading require verification.

## Stuck recovery (v0.2.8)
Each worker saves its initial spawn block; legacy workers use their last persisted anchor on upgrade. After 15 seconds of unsuccessful loaded-target work attempts (30 action cycles at 20 TPS), release the assignment and return to the saved home or a nearby collision-free loaded position. Keep progress and undo history, retry work, and reset the retry counter after successful work. Other team members continue. Three failed recovery cycles without successful work block the project instead of looping indefinitely. Home chunk/safe position wait is bounded to 120 action cycles. Configuration: `-Dnpcarchitects.stuckSeconds=15` (1–3600) and `-Dnpcarchitects.stuckRetries=3` (1–20). Ordinary unloaded-target waits do not count as stuck. Protected blocks still block immediately. Runtime verification required.

## Manual respawn (v0.2.8)
Operator commands: `/architect respawn <id>` queues the whole team; `/architect respawn all` queues every nonterminal project; `/architect respawn <id> <worker>` queues a single 1-based team slot (1 is primary); `/architect status <id>` shows the stable slot roster, home, UUID and pending recovery. Commands work from console or player in any dimension. Requests persist across restarts; project status, IDs, plan and undo are unchanged. Work pauses for the affected project while its queued replacements are processed. Replacements use existing safe spawn search near the saved home (solid footing, loaded chunks, clear headroom), retire old UUIDs before removing old entities, and preserve team size. If no safe spot or home chunk becomes available within 120 management cycles, report failure and retain the original worker. Terminal jobs are excluded. Older saved workers retain their migrated home anchors. Runtime verification required.

## v0.2.8 — distributed work
Default adaptive recursive footprint zones, alternatives quadrants, strips and chunk-sized local tiles. `/architect distribution <id> <adaptive|quadrants|strips|chunks>`, `/architect spacing <id> <0..64>` (default 8), `/architect rebalance <id>`, `/architect zones <id>` (current assignments with requester-only colored target particles within 96 blocks). Settings persisted per job, old saves default adaptive. Build layers indexed incrementally at 8192 cells per management cycle, per-zone preferred assignments and work stealing when empty; distance separation is a soft preference, not a physical collision guarantee. Team additions invalidate the index automatically. Existing layer barriers, durable completion indices, undo, protection and recovery preserved. Clearing remains constrained to existing safe top-down active slice; spreads assignments within that slice, not independent distant clearing strips. Chunk mode uses footprint-relative 16-block tiles, not world-aligned chunks. Zones recomputed from stable roster; current reservations transient. No live Minecraft verification yet.

## v0.2.8 — exclusive world chunks
Multi-worker jobs now enforce one active worker per actual world-aligned chunk in both clearing and building. Modes influence preferred chunk selection, not permission to share a chunk. Choose separated unclaimed chunks; release when exhausted or worker unavailable. Clearing walks each assigned chunk top-down per column, preserving legacy clear indices and durable out-of-order completion. Building retains the global bottom-up layer barrier. Workers idle when fewer eligible chunks than workers. Existing spacing command remains stored but strict chunk separation supersedes soft spacing. Physical travel and stand positions may cross chunk boundaries. `/architect zones <id>` reports owned chunks and targets. Ownership is transient and reconstructed from saved completion indices. Survey unchanged. Large clears may grow the existing JSON clearDone set substantially until gaps close. Live test pending.

## v0.2.8 — independent chunk lifecycle
Every worker (including single-worker jobs) reserves a world chunk, clears its footprint top-down, builds the same chunk bottom-up using original plan order, then releases it and claims another unfinished chunk. Other workers can clear/build concurrently; no global clearing or layer barrier. Survey remains a whole-site safety prerequisite. Existing saved indices and undo histories are preserved; old building jobs migrate as already cleared, and partial clearing/building resumes from saved indices. `/architect zones <id>` shows CLEARING/BUILDING/WAITING and actual chunk. Unsupported block states are deferred for 5 seconds so other chunks can supply support; permanently unsupported or same-chunk ordering-dependent states may require manual intervention. No final full schematic verification yet. Progress sets can grow for large out-of-order jobs. Test on backup first; not compatible with downgrading active independent jobs to older versions. CI and live testing pending.

## v0.2.8 — faster block actions
`-Dnpcarchitects.workIntervalTicks=4` (default, clamped 2–20): work/management cadence is four ticks instead of ten. At 20 TPS theoretical per-worker action ceiling rises from 2 to 5 blocks/s, or 10 at interval 2. At most one mutation per worker per cycle including phase transition. Chunk ownership, reach, collision, protection and per-mutation persistence remain intact. Stuck/recovery/respawn attempt limits rescaled to preserve nominal tick-based timeouts. More frequent management and synchronous JSON saves can increase server load; tune interval upward if TPS drops. Server package JVM defaults now -Xms4G -Xmx8G; existing installations must manually merge those flags, preserving local settings. Actual throughput and memory are not measured. CI/runtime pending.

### Ground-aligned schematic placement (v0.2.8)
New schematic previews and builds align the lowest non-air layer to the block below the recorded `/architect pos1` feet position (or current feet with the existing +3 X/Z fallback). Empty bottom layers are trimmed from new plans, preserving all other relative coordinates. Origin and trimmed layer count are reported before placement. Existing persisted jobs are not moved or modified. For an elevated build, select pos1 at one block above the desired foundation Y. This is coordinate-based, not terrain surface detection; stand on a full ground block for normal placement.

## v0.2.8 — snow-aware spawning
Initial spawning, adding workers, and replacement/respawn now share collision-checked spawn candidates on air or vanilla snow layers above sturdy ground. Snow is left intact; worker feet are positioned at its fractional surface height. Initial workers search within three blocks if the player's position is occupied. Team additions retain eight-block search radius and all-or-nothing behavior. Home recovery recognizes fractional snow height. Schematic origin unchanged. Forge compilation and live snow-layer testing pending.
